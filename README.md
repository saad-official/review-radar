# Review Radar

App-store reviews in; themes, policy-checked reply drafts and evidence-backed GitHub issue
proposals out. A workflow-first agent whose every write waits for a human.

Level 3 project of the AI Engineering Journey (Phase 3: agents and tool use), app 9 of the
Vibe Build Series. Build contract: [docs/spec.md](docs/spec.md).

- Web: https://getreviewradar.vercel.app · API: https://review-radar-api.vercel.app (`/api/docs`)
- Demo app: Spotify (App Store, US), public reviews from Apple's RSS feed.

## What it does

Add an app (App Store id, or CSV import for Google Play). A run fetches new reviews,
extracts signals from each (category, sentiment, severity, devices and versions mentioned,
verbatim quotes), clusters them into themes with embeddings (joining existing themes
first), then an agent loop proposes replies and GitHub issues. Every proposal waits in an
approval queue with its evidence and reasoning; approved issues are created in the app's
repository, approved replies are exported as CSV. The agent remembers what was triaged and
what a human rejected, so nothing is proposed twice. Every run leaves a trajectory the UI
replays step by step.

## How it works

```
fetch -> extract (10 reviews/call) -> embed -> cluster (memory first) -> propose (tool loop) -> finish
   every step -> run_steps (append-only trajectory)          proposals -> human -> executors
```

[llm-kit](https://github.com/saad-official/ai-engineering-journey/tree/main/packages/llm-kit)

`gemini-3.5-flash-lite` as fallback, Voyage `voyage-4-lite` (1024-d) for embeddings
(`gemini-embedding-001` 768-d still selectable; [decision 0005](docs/decisions/0005-voyage-embeddings.md)).

## Learning: explain it back

**1. Why can the agent not write anything?**
Because the dangerous input (reviews written by strangers) and the dangerous output
(issues in your tracker, replies in your name) must never be connected by a model alone.
The agent's two write tools only insert rows with status `proposed`; the executors that
touch GitHub live in a package the agent never imports, and run only from the approve
endpoint, on the stored proposal, with the operator's token. A model that is wrong, or
manipulated, produces a bad proposal in a queue next to its evidence and reasoning. That
is a cheap failure. Without the gate, the same mistake is an incident.

**2. Why budgets and deadlines, and why three of them?**
Each guards a different failure. `max_iterations` (24) stops a model that keeps calling
tools without converging. The deadline (200 s, less if the serverless request has less)
stops a provider that hangs: three slow turns pass an iteration cap easily. The ledger
ceiling ($0.10 per run, checked *before* each call) stops spend, including the extraction
and embedding calls before the loop. A run that hits one is not a crash: the trajectory
records why it stopped, the work done is kept, and the next run continues.

**3. Why is memory just tables?**
What the agent must remember is concrete and relational: which themes exist, which reviews
belong to them, what was proposed, what a human decided and why. Postgres already holds
that, with constraints. `search_memory` reads it (full text plus pgvector, fused), and
unique indexes make "one issue proposal per theme, ever" a database fact, so a rejected
proposal cannot come back even if the model ignores memory. A transcript store or a
model-written summary would be lossy, unauditable, and poisonable by a review.

**4. How is a prompt injection in a review contained?**
In four layers, none trusted alone. Obvious injections are quarantined by a deterministic
detector and never sent to any model. Everything else is wrapped in tags the review text
cannot close, under prompts that say tagged text is data. The tools accept only ids this
run handed out and validate every argument; evidence must be verbatim from the theme's
reviews, and instruction-like titles are refused. Finally, whatever gets through is only a
proposal a human reviews. The tests run an agent that obeys any instruction it can see: it
produces no issue from the injected review.

## Live

- Web: https://getreviewradar.vercel.app · API: https://review-radar-api.vercel.app (`/api/docs`)
- Demo app on 5 Oct 2026: Spotify (App Store, US) with 200 public reviews ingested and 30 analysed. The agent run that proposes replies and issues is waiting on model quota (Groq and Gemini daily free limits were spent on evals on 4 Oct) and on a GitHub token for `saad-official/review-radar-demo-issues`; write actions need the operator token.
- Measured so far: extraction accuracy on 30 labelled reviews: category 93.3%, sentiment 96.7%, device-info 100% (keyword baseline 70% / 83%); extraction cost $0.0081 for 30 reviews on Gemini. Trajectory rules pass on the recorded partial run.

**Live agent run verified on 5 Oct 2026** (after switching embeddings to Voyage): 30 reviews analysed, 4 themes created, 4 replies and 1 issue proposed in 8 model turns and 11 tool calls for $0.0065 at paid rates, every trajectory rule passing. Approving the issue through the API created [review-radar-demo-issues #1](https://github.com/saad-official/review-radar-demo-issues/issues/1) ("Reduce ad frequency for free tier"); an approved reply appeared in the CSV export and a rejection stored its reason as memory.
